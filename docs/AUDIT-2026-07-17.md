## Primary-source criteria

The audit uses current first-party guidance rather than a generic architecture
template:

- [Managing model data in your app](https://developer.apple.com/documentation/SwiftUI/Managing-model-data-in-your-app): keep a clear source of truth, separate model data from views, and use Observation where the deployment target permits it.
- [SwiftUI model data](https://developer.apple.com/documentation/swiftui/model-data): keep transient state local, use bindings for parent-owned value state, and expose reference model data deliberately.
- [Understanding and improving SwiftUI performance](https://developer.apple.com/documentation/Xcode/understanding-and-improving-swiftui-performance): keep view-body work bounded and reduce unnecessary dependency-driven updates.
- [Testing in Xcode](https://developer.apple.com/documentation/xcode/testing): preserve a test pyramid with many fast isolated tests, fewer integration tests, and focused UI tests for critical user flows.
- [Adding tests to an Xcode project](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project): use Swift Testing or XCTest for unit/integration coverage and XCTest/XCUIAutomation for UI behavior.
- [Writing and running performance tests](https://developer.apple.com/documentation/xcode/writing-and-running-performance-tests): measure performance-critical paths and establish explicit regression baselines.
- [Migrating to Swift 6](https://www.swift.org/migration/): adopt compile-time data-race safety deliberately and incrementally.
- [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/): optimize public APIs for clarity at the point of use and document their contracts.
- [Designing for iOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-ios/): emphasize the primary task, keep secondary actions discoverable, and adapt to appearance, orientation, and Dynamic Type.
- [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/): support larger text, avoid color-only communication, and verify the semantic interface with accessibility tools.

## Repository map

The codebase already has a sound high-level separation:

| Layer | Location | Responsibility |
| --- | --- | --- |
| Rules engine | `Sources/PreferansEngine` | Pure domain state, reducers, scoring, bots, scripts, invariants |
| Projection | `Preferans/Projection` | Per-viewer information boundary and legal-action projection |
| App orchestration | `Preferans/GameViewModel.swift`, `Preferans/Online` | Local pacing, host authority, transport, persistence, reconnection |
| SwiftUI | `Preferans/UI` | Lobby, table, waiting room, settings, sheets, reusable presentation |
| Fast tests | `Tests/PreferansEngineTests` | Engine, projection, coordinator, layout, persistence contracts |
| UI tests | `PreferansUITests` | Accessibility contracts, critical flows, screenshot capture |
| Worker | `workers/room-worker` | Room durability, authorization, and relay behavior |

The main architectural risk is not a missing layer. It is that several files
still aggregate too many concerns within those layers.

## Test-suite audit

Current strengths:

- 284 test methods cover rules, scoring variants, invariants, event sourcing,
  projections, layout, online authority, reconnection, worker integration, and
  end-to-end scripted matches.
- Structural snapshots protect viewer visibility, seat order, talon exposure,
  and trick placement without turning every change into a pixel diff.
- `MatchUIRobot` centralizes accessibility identifiers and domain actions.
- UI loops have explicit step limits, and the production/test/demo bot pacing
  constants are centralized in `BotPacing`.

Completed test-harness improvements:

1. Build/test/screenshot helpers fail immediately with one actionable Xcode
   prerequisite instead of surfacing downstream package errors.
2. Screenshot playthroughs dedupe by meaningful phase/viewer/deal state.
3. Settings language persistence and presentation contracts are covered.
4. Onboarding has a deterministic Accessibility XXXL navigation test; UI
   automation no longer depends on persisted onboarding or ATT prompt state.
5. Stateful deal sources have concurrent-access regression coverage.

Remaining gaps:

1. Run the pending test/UI suites with full Xcode and resolve any compiler or
   runtime failures before treating parser/type-check evidence as sufficient.
2. Add bounded performance baselines only after the normal suite is green;
   never replace an algorithmic bound with a longer wrapper timeout.
3. Extend large-content-size UI coverage from onboarding to lobby, waiting
   room, settings, and the table's primary action surfaces.
4. Preserve critical UI happy paths, but keep combinatorial rule coverage in
   the engine/coordinator layer.

## Completion criteria

- the matching Xcode toolchain builds both package and app;
- fast tests, worker tests, focused UI tests, and full bounded UI validation
  pass;
- every changed screen has a fresh before/after pair in the matrix;
- large-file splits reduce responsibility count rather than only moving text;
- concurrency annotations are compiler-checked instead of assumed;
- accessibility and large-text states have been inspected;
- every semantic chunk has its own commit; and
- this register contains no unowned P0/P1 item.
